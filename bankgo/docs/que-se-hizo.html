DOCUMENTACIÓN TÉCNICA

Qué se implementó en BankGo

Documentación completa de la implementación. Todos los fragmentos de código son reales, copiados de los archivos del proyecto. Esta documentación fue generada leyendo el código fuente, no inventada.

Sección 1 — Arquitectura

BankGo implementa una arquitectura de 3 capas con separación estricta de responsabilidades. Cada capa solo conoce a la capa inmediatamente inferior.

PRESENTATION LAYER — app/

Pantallas React Native. Solo renderiza UI y despacha acciones a los stores. No contiene lógica de negocio. Usa expo-router para navegación file-based.

_layout.tsx(auth)/login.tsx(app)/dashboard.tsx(app)/transfer.tsx(app)/cards.tsx(app)/account/[id].tsx
↕ suscripción a stores
DOMAIN LAYER — src/stores/

Stores Zustand. Contienen estado de la aplicación y lógica de negocio (validaciones, transformaciones, decisiones de UI). Orquestan las llamadas a la infraestructura.

useAuthStore useAccountsStore useTransactionsStore useTransferStore useCardsStore
↕ llamadas a servicios
INFRASTRUCTURE LAYER — src/services/

Implementaciones de I/O: cliente HTTP (apiClient/devClient), autenticación (authService, pkce, tokenStore), cache (cacheService). Sin lógica de UI ni de negocio.

client.ts devClient.ts handlers.ts authService.ts pkce.ts cacheService.ts

Por qué esta arquitectura

Separación de concerns: Un cambio en la API solo afecta src/services/api/. Un cambio en el diseño visual solo afecta app/. Un cambio en las reglas de negocio solo afecta los stores.

Testabilidad: Los stores son funciones puras de Zustand — se pueden probar sin montar componentes React. La infraestructura se mockea en tests sin afectar los stores ni la UI.

Escalabilidad: Agregar una nueva pantalla = agregar un archivo en app/ + suscribirse a stores existentes. Agregar un nuevo dominio = agregar un store + un endpoint en el cliente.

ADRs — Decisiones de Arquitectura

ADR-001
React Native + Expo sobre Flutter o nativo puro
Decisión: React Native 0.81 + Expo SDK 54. TypeScript end-to-end. Módulos nativos pre-compilados (expo-crypto, expo-secure-store). Expo Router para file-based navigation.
Trade-off aceptado: Performance inferior a Flutter en listas muy largas. FlatList vs FlashList pendiente.
ADR-002
Zustand sobre Redux Toolkit o Context API
Decisión: Zustand v5, un store por dominio. Sin dispatch, sin reducers, sin Provider. create<State>() con acciones async inline.
Trade-off aceptado: Sin Redux DevTools nativo. Menos convenciones de equipo predefinidas.
ADR-003
MSW v2 sobre JSON Server o Axios Mock Adapter
Decisión: MSW v2 con handlers TypeScript tipados. Un solo código para dev y test. Intercepta fetch() real. Estado in-memory stateful sin proceso externo.
Trade-off aceptado: Sin persistencia entre reinicios de MSW.
ADR-004
AsyncStorage (cache) separado de SecureStore (tokens)
Decisión: Threat model diferente. SecureStore = OS Keychain (iOS Keychain Services, Android Keystore). AsyncStorage = SQLite plano para cache no sensible.
Trade-off aceptado: AsyncStorage no cifrado en dispositivos rooteados.
ADR-005
expo-crypto para PKCE sobre implementación manual
Decisión: Crypto.getRandomBytes() usa SecRandomCopyBytes (iOS) / SecureRandom (Android). SHA-256 nativo del OS. No añade dependencias al bundle.
Trade-off aceptado: Requiere mock en Jest (no corre en Node puro).

Sección 3 — Sistema de Autenticación PKCE

¿Qué es PKCE y por qué en mobile?

PKCE (Proof Key for Code Exchange, RFC 7636) es una extensión del flujo OAuth 2.0 que resuelve un problema específico de las apps mobile: las apps mobile no pueden guardar client secrets de forma segura porque el APK/IPA es descompilable.

PKCE reemplaza el secret estático con un par de valores derivados criptográficamente en cada sesión: el code_verifier (secreto) y el code_challenge (hash del verifier). El servidor solo recibe el challenge — nunca puede ser usado para otro ataque.

Implementación en pkce.ts

src/services/auth/pkce.ts — código completo expo-crypto nativo
// URL-safe base64 — RFC 4648 §5, sin padding function toBase64Url(buffer: Uint8Array): string { let binary = ''; for (let i = 0; i < buffer.length; i++) { binary += String.fromCharCode(buffer[i]!); } return btoa(binary) .replace(/\+/g, '-') .replace(/\//g, '_') .replace(/=+$/, ''); // ← sin padding = (requisito del RFC) } // generateCodeVerifier — RFC 7636 §4.1 // 32 bytes aleatorios criptográficamente seguros → 43 chars base64url export async function generateCodeVerifier(): Promise { const bytes = Crypto.getRandomBytes(32); // SecRandomCopyBytes en iOS return toBase64Url(bytes); } // generateCodeChallenge — RFC 7636 §4.2 // SHA-256 del verifier codificado en base64url export async function generateCodeChallenge(verifier: string): Promise { const digest = await Crypto.digest( Crypto.CryptoDigestAlgorithm.SHA256, new TextEncoder().encode(verifier), ); return toBase64Url(new Uint8Array(digest)); } // generateState — CSRF token, 16 bytes → 32 hex chars export async function generateState(): Promise { const bytes = Crypto.getRandomBytes(16); return Array.from(bytes) .map((b) => b.toString(16).padStart(2, '0')) .join(''); }

authService.ts — login completo

async login(email: string, password: string): Promise<void> { const verifier = await generateCodeVerifier(); const challenge = await generateCodeChallenge(verifier); const state = await generateState(); const response = await apiClient.post<TokenResponse>('/auth/token', { email, password, code_challenge: challenge, code_challenge_method: 'S256', state, }); const expiresAt = Date.now() + response.expires_in * 1000; // Tokens SOLO en SecureStore — nunca en AsyncStorage ni en logs await SecureStore.setItemAsync(KEYS.ACCESS_TOKEN, response.access_token); await SecureStore.setItemAsync(KEYS.REFRESH_TOKEN, response.refresh_token); await SecureStore.setItemAsync(KEYS.EXPIRES_AT, String(expiresAt)); // Hidratar memoria para requests inmediatos tokenStore.setTokens(response.access_token, response.refresh_token); console.warn('[Auth] Login completed'); // ← NUNCA loguea el token real }

Restore de sesión (app restart)

Cuando la app reinicia, _layout.tsx llama a initialize() que llama a authService.restoreSession(). Este método lee los tokens de SecureStore y verifica que no estén expirados:

async restoreSession(): Promise<boolean> { const [accessToken, refreshToken, expiresAtStr] = await Promise.all([ SecureStore.getItemAsync(KEYS.ACCESS_TOKEN), SecureStore.getItemAsync(KEYS.REFRESH_TOKEN), SecureStore.getItemAsync(KEYS.EXPIRES_AT), ]); if (!accessToken || !refreshToken || !expiresAtStr) return false; const expiresAt = parseInt(expiresAtStr, 10); if (isNaN(expiresAt) || expiresAt <= Date.now()) { await authService.logout(); // limpiar tokens expirados return false; } tokenStore.setTokens(accessToken, refreshToken); return true; }
El _layout.tsx inicializa isLoading: true mientras se restaura la sesión para evitar un "flash" de redirección al login cuando el usuario tiene sesión activa.

Sección 4 — Mock API

devClient.ts — Para dispositivo/emulador

En Expo Go, MSW (msw/node) no puede interceptar fetch() porque Node no está disponible en el runtime del device. La solución: un cliente que implementa la misma interfaz que apiClient pero sirve datos directamente desde memoria, sin ninguna llamada de red.

// Selección automática en client.ts: export const apiClient = typeof __DEV__ !== 'undefined' && __DEV__ && process.env['NODE_ENV'] !== 'test' ? devApiClient // ← device/emulador: sin red : httpApiClient; // ← tests: fetch real, MSW intercepta

El devClient mantiene estado mutable en memoria — el estado de congelamiento de tarjetas y las transferencias creadas persisten durante la sesión del emulador.

MSW handlers.ts — Para tests

En el entorno de Jest, el httpApiClient real hace fetch() y MSW lo intercepta antes de que salga a la red. Los tests ejercitan exactamente el mismo código de producción.

// Latencias realistas (sin ralentizar los tests demasiado) const FAST = (): Promise<void> => delay(200 + Math.random() * 200); const MEDIUM = (): Promise<void> => delay(600); const SLOW = (): Promise<void> => delay(1200); // Auth guard reutilizable en todos los handlers function requireAuth(request: Request): boolean { const auth = request.headers.get('Authorization'); return auth === `Bearer ${MOCK_ACCESS_TOKEN}`; } // Log sin tokens — solo confirma que el exchange ocurrió console.debug('[MSW] auth/token: exchange successful, tokens=[REDACTED]');

Sección 5 — Stores Zustand

¿Por qué Zustand?

Context API re-renderiza todo el árbol cuando cualquier valor cambia. Redux Toolkit requiere ~120 líneas de boilerplate (slice + actions + selectors + Provider) por dominio. Zustand ofrece el mismo poder en ~40 líneas, con acceso fuera de React (useStore.getState()) y re-renders selectivos.

Sección 6 — Cache Offline

El cacheService es una abstracción sobre AsyncStorage que agrega TTL (Time-To-Live) y serialización/deserialización automática. Cada entrada tiene un campo expiresAt que se verifica al leer.

src/services/cache/cacheService.ts — interfaz completa
interface CacheEntry<T> { data: T; cachedAt: number; // cuando se escribió expiresAt: number; // cuando expira (cachedAt + ttlMs) } // get() verifica TTL antes de retornar async get<T>(key: string): Promise<T | null> { const raw = await AsyncStorage.getItem(key); if (raw === null) return null; const entry = JSON.parse(raw) as CacheEntry<T>; if (Date.now() > entry.expiresAt) { await AsyncStorage.removeItem(key); // auto-limpieza return null; } return entry.data; } // Claves de cache usadas en el proyecto: keys: { accounts: (): string => 'bankgo:accounts', transactions: (accountId: string, page: number): string => `bankgo:transactions:${accountId}:${page}`, } // TTL por tipo de dato: TTL: { accounts: 5 * 60 * 1000, // 5 minutos transactions: 2 * 60 * 1000, // 2 minutos }

¿Qué pasa cuando no hay red?

1. El store intenta apiClient.get().
2. La llamada lanza una excepción (Network request failed).
3. El catch lee el cache con cacheService.get(key).
4. Si el cache existe y no está expirado: set({ accounts: cached, isOffline: true }).
5. La UI muestra los datos con un banner naranja "Sin conexión".
6. Si no hay cache (primera apertura sin red): error visible con botón Retry.

Sección 8 — CI/CD Pipeline

El pipeline corre en GitHub Actions en cada push y PR a las ramas main y develop. Tiene 2 jobs en secuencia: primero calidad, luego build.

📋 Job 1: quality
→ Checkout + Setup Node 20
→ npm ci --legacy-peer-deps (lock file exacto)
→ npx tsc --noEmit (TypeScript)
→ npm run lint (ESLint)
→ npm test -- --coverage (25 tests)
→ Upload coverage artifact (7 días)
→
🏗 Job 2: build (needs: quality)
→ Solo corre si quality pasa
→ Checkout + Setup Node 20
→ npm ci --legacy-peer-deps
→ npx expo export --platform web
(validación de que el bundle compila)

¿Por qué este orden?

  • TypeScript antes que tests: un error de tipos puede hacer que los tests pasen por razones equivocadas (any silencioso).
  • Lint antes que tests: ESLint detecta código muerto y anti-patterns que los tests no verifican.
  • Tests con coverage: el artifact de coverage es descargable para inspección post-merge.
  • Build separado con needs: quality: no tiene sentido validar el bundle si hay tests fallidos. El build puede tardar 2-3 min — no desperdiciar CI si la calidad ya falló.

Sección 10 — Seguridad OWASP Mobile Top 10

M1 ✓
M1 — Improper Credential Usage
PKCE RFC 7636 implementado con expo-crypto (criptográficamente seguro). Tokens persistidos exclusivamente en expo-secure-store (OS Keychain). La contraseña viaja una sola vez en el body del POST /auth/token y jamás se almacena. tokenStore loguea [REDACTED] en vez del valor real.
M2 ✓
M2 — Inadequate Supply Chain Security
package-lock.json garantiza versiones exactas. CI usa npm ci (no npm install) que respeta el lock file y falla si hay divergencias. Dependencias mínimas del ecosistema Expo (bien auditadas).
M4 ✓
M4 — Insufficient Input/Output Validation
Validación en dos capas: transferStore.validate() antes del POST (client-side), y el handler MSW valida y retorna 422 VALIDATION_ERROR si falla (server-side). Saldo verificado antes de enviar la transferencia.
M8 ✓
M8 — Security Misconfiguration
logger.ts sanitiza 4 patrones antes de imprimir:
const SENSITIVE_PATTERNS = [ /Bearer\s+[\w.-]+/gi, /access_token["\s:=]+[\w.-]+/gi, /refresh_token["\s:=]+[\w.-]+/gi, /password["\s:=]+"[^"]+"/gi, ];
En producción (__DEV__ === false), solo los errores se imprimen.
M9 ✓
M9 — Insecure Data Storage
Separación estricta por threat model: SecureStore para tokens (OS Keychain, cifrado por hardware) — AsyncStorage solo para cache de datos de negocio (saldos, transacciones) que no constituyen credenciales de acceso. Nunca se almacenan números de cuenta completos, contraseñas ni PII en AsyncStorage.
